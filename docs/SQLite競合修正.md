# SQLite競合による停止の修正

通常の状態保存と、終了CSV・Viewer資料の出力は別の接続から同じSQLiteへ書き込みます。従来は状態保存のトランザクションで先に読み取り、その間に出力側が書き込むと、保存側が書込みへ切り替えられず停止する経路がありました。初回接続だけに設定した待機時間等が、接続交換後には失われる問題もありました。

提示された新規約定の表示は通常ログです。その後に戦略状態・約定反映位置の保存が続くため、その保存で失敗すると最後の通常表示が新規約定になります。実際に停止したDBやスタックは未取得なので、個別障害の原因がこの一経路だけだったとは断定しません。

## 修正

- 書込み用トランザクションは、読取り前に `BEGIN IMMEDIATE` で書込み予約を取ります。本体保存・終了CSV・Viewer出力の接続を共通化しました。
- `busy_timeout=5000`、`synchronous=FULL`、`foreign_keys=ON` を接続文字列へ定義し、新しい物理接続にも適用します。WALの有効化と確認は維持します。
- 既存DBを読む出力処理は `mode=rw` を維持し、存在しないDBを勝手に作りません。読取専用の診断には書込み予約を強制しません。
- 待機を越えた競合やI/O障害はエラーとして残します。注文の再送、保存済み約定の再作成、DB削除による回避は行いません。
- 保存失敗には商品と保存フェーズを付け、商品workerの異常終了を画面・操作記録に加えてコンソールにも表示します。

読取スナップショットを後から書込みへ切り替えられない場合があることと、IMMEDIATEによる事前の書込予約は、[SQLiteの分離仕様](https://www.sqlite.org/isolation.html)と[トランザクション仕様](https://www.sqlite.org/lang_transaction.html)に基づきます。接続文字列は使用中の[modernc.org/sqlite v1.36.3](https://pkg.go.dev/modernc.org/sqlite@v1.36.3#Driver.Open)の仕様を確認しています。

## 確認した範囲

旧DEFERRED順序で `SQLITE_BUSY_SNAPSHOT` の517、別writerの予約中で `SQLITE_BUSY` の5を人工再現しました。新方式では開始時に待機して保存し、接続交換後の設定も維持します。期限超過時には状態・約定・監査イベントが途中確定しないことも確認します。

本体保存と別接続のCSV・Viewer出力を並行反復し、30所有玉・60約定について本文・順序・所有ID・金額・手数料・出力件数を照合しています。全パッケージの試験と静的検査も実施します。試験は人工データと一時DBだけを使用し、実注文APIへ接続しません。

さらにWebの出力監視と同じ保存先・同じ出力処理を使い、DBを開いたまま40所有玉・80約定を並行保存しました。正本の順序、CSV・Viewerの全件数・所有ID・損益、最終的な出力エラー解消を確認しています。売買workerやcontrollerは呼びません。

配布版は別の一時フォルダへ実行ファイル・設定・ルールだけを配置して起動し、設定検査、全5商品OFF、画面とREST APIを確認しました。controllerへの要求は0件です。Windowsで実起動し、Linux版はビルド確認を行っています。

これは競合の回帰試験であり、実時間で丸一日放置した確認ではありません。SQLite形式・手法ID・売買条件・CSV/JSONLの契約は変更していません。

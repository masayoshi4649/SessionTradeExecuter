# 運転と保存

配布先は `dist/{windows|linux}-amd64/SessionTradeExecuter/` です。一つの実行ファイルから5商品を個別にOFF・DryRun・ONへ切り替えます。操作は[Web版](Web版.md)、標準時間帯は[新標準手法](新標準手法.md)、終了CSVは[セッション損益](セッション損益.md)を参照してください。

## 起動

Windowsは `session-trade-executer.exe`、Linuxは `./session-trade-executer` を引数なしで起動します。実行ファイルの隣の `conf/*.toml` だけを読み、作業フォルダ側の設定へ切り替わりません。`conf` がなければ停止します。ソースからは `go run ./cmd/build-dist` で配布物を作り、設定と同じフォルダにある実行ファイルを起動します。`go run .` は通常起動には使いません。SQLiteは純Go実装で、MinGW・Cコンパイラ・外部SQLiteサーバーは不要です。

`startup.action="run"` は通常運転、`check` は通信なしの設定検査、`probe` は読み取り接続検査、`diagnostics` は既存SQLiteだけから診断ZIPを出力する操作です。いずれもCLI引数ではなく設定で選びます。検査後に通常運転へ戻す場合は `action="run"` に戻します。

新規配布の全5商品はOFFです。商品ごとの `mode="dryrun"` は仮想売買、`mode="live"` は実注文です。保存済みモードは次回起動にも適用するため、毎起動OFFへ強制変更する仕様ではありません。片方向上限は新規配布で日経mini・TOPIXminiが10枚、日経microが20枚、両ラージが2枚です。既存の数量・モード・時間帯・改変ルールは更新時も保持します。

判断には日経225・TOPIXのラージを参照し、商品ID・限月・立会時刻はcontrollerから取得します。日経3商品の現在の標準と商品ごとの時間帯は[時間帯切替](時間帯切替.md)を参照してください。商品別の注文・建玉・台帳は同一アプリ内のworkerで分離します。

## 時間による切替

次の未参加追加・主担当静観は旧T06/T04/U06の構成です。TG04/PG04は担当ごとに異なる入口を使い、夜間の米国開始前後15分は全担当を返済・静観の対象とします。場内返済の時刻は両構成に共通です。

| 項目 | 初期設定 |
|---|---|
| 日中の未参加時追加 | 日本時間12:30以降 |
| 夜間TOPIXの未参加時追加 | 日本時間で冬翌01:30・英国夏時間翌00:30以降 |
| 夜間日経の未参加時追加 | 米国開始の30分後。日本時間で冬翌00:00・米国夏時間23:00 |
| 夜間主担当の静観 | 米国現物開始の前後15分。追加担当には適用しない |
| 全担当の場内返済 | APIで取得した立会終了の10分前 |
| 追加の新規期限 | 場内返済のさらに10分前 |

日本の開始・終了・送信可能時間をプログラムで固定せず、controllerの立会情報に従います。米国と英国の夏時間はそれぞれの地域で計算します。タイムゾーン情報を実行ファイルへ同梱し、Windows/Linuxで同じ時計を使います。

時刻は `[schedule]` の `_jst` 項目へ日本時間で指定します。米国基準23:30・ロンドン連動01:30は冬の日本時間で、夏は各地域に従って自動で1時間早めます。昼夜の手法は `[methods]` の `day`・`night` で指定し、静観秒数・追尾幅などはその手法に含めます。配布物では `conf/settings.toml` 内にあります。ソース直下の `conf` では、それぞれ `system.toml`・`algorithm.toml` です。変更後は `startup.action="check"` で起動して検査してください。

## 途中起動・再起動

1. 実注文では、旧台帳で所有を確認できる未確定注文・条件予約だけを取り消します。取消受付で終了とせず、途中の部分約定と注文終了を照合します。結果不明なら旧状態を保持して起動を止めます。
2. 旧状態を監査用に残し、全約定履歴を保持したまま、新しい注文名前空間と空の建玉・候補・残玉予算へ原子的に切り替えます。前回の実建玉は自動返済せず手動管理へ移します。仮想運転では旧仮想玉を引き継がず、清算を捏造しません。
3. 口座・登録一覧と確定足、二市場の当場生板を取得し、同じセッション・世代のデータで特徴量だけを準備します。履歴から過去の売買や候補状態を作り直しません。
4. 準備後の新鮮な板から今回の新規・継続・返済を判断します。履歴が十分で条件が成立すれば、起動後すぐに新規注文が出ることがあります。

毎回の起動でこの手順を使います。前回の実建玉・手動建玉・他媒体の注文を今回の所有物へ採用しません。片方向上限も今回の所有玉だけを対象にするため、旧建玉1枚と新上限10枚なら口座全体で11枚の保有が可能です。旧実建玉の返済は利用者が管理します。

履歴には元の受信時刻がないため、暖機では原価格時計と足の名目公開遅延を使います。実際の取得時刻は別に保存します。ライブ中の足は実受信時刻を使い、未確定足を判断に使いません。

寄り付き前の起動で「採用0行」になるのは、前場の価格を当場の判断へ混ぜないためです。08:45以降の板・確定足は引き続き取り込みます。「履歴同期完了」は通信履歴の同期完了で、売買指標がすべて揃ったことを意味しません。

旧T06とTG04/PG04の基本担当は60本EMAと3本分の傾き、自己60秒・相手追加60秒の公開待機を使います。08:45開始の当場だけを使うため、両市場の方向判定が可能になるのは最短でも概ね09:50です。TG04/PG04の他担当は独立した準備・入口を持ち、この時刻を一律の取引開始時刻にはしません。

画面とSQLiteのイベントへ、既定30秒ごとに「稼働」を記録します。参照板・発注商品の最終受信時刻、最終判断時刻、受信・判断の累計行数、保有枚数、待機理由を確認できます。`trace.jsonl`は生成しません。間隔は `runtime.status_seconds` で変更できます。価格時計が不正、口座情報が古い、商品板が未受信といった場合も理由を表示します。

画面は `[稼働/dryrun] NK225micro（参照NK225）` のように、運転モード・発注商品・参照ラージを区別します。`仮想保有 買0・売10枚` は今回の運転で成立した仮想約定の残数であり、実口座の枚数ではありません。再起動時は0枚から始めます。実注文モードの `[稼働/live]` と `実約定保有` も、今回の起動で所有を確認した残数だけを示します。旧実建玉や手動建玉を含む口座全体の残数ではありません。SQLiteの稼働記録には `dryrun` と `position_source`、新規・返済の画面にも `[dryrun]` / `[live]` を付けます。

仮想と実注文は売買条件を共用しますが、建玉・注文・戦略はモード別に保存します。どちらも毎起動を空から始め、`dryrun=false` に変えても仮想注文を実送信しません。起動時点とその後の実約定が異なれば、売買結果も異なります。プロセスを止めずに通信が一時切断した場合は、今回の所有状態を保持して再同期します。これは新しい起動とは区別します。

同じ保存先の二重起動に加え、同一OSユーザー・同一一時領域・controller URL・商品・モードの重複もOSロックで拒否します。異なるユーザー・ホスト・一時領域やURL別名間の排他は保証できないため、同一商品を重複運転しないでください。新規起動では枚数・手法・時刻設定を変更できますが、旧台帳の商品・モードが異なる保存先は拒否します。**運転中の設定変更は自動反映しません**。

## 中断・終了

エラー終了時は、停止理由を画面と実行ファイル隣の `log/error.log` に日時付きで残します。設定ファイルの読込に失敗しても記録できるよう、このエラーログの場所は固定です。Windowsで実行ファイルを直接開いた場合は、Enterキーを押すまでエラー画面を保持します。PowerShell・cmdなど既存端末からの実行、標準入出力のリダイレクト、Linuxでは入力待機せず終了コード1を返します。正常終了は確認待ちをしません。ログが書込不能でも、元の停止理由と保存失敗を画面に表示します。

例えば片方向上限20枚から10枚へ変更して再起動すると、新しい運転は上限10枚で空から始まります。旧実建玉を新上限へ合わせて自動返済する処理はありません。旧未確定注文の終了確認ができない場合は、設定を変えても起動できません。

短い受信断では直ちに全返済せず、新規を止めて再接続します。初期設定の180秒を超えてラージの受信が途絶えた場合は、返済要求を保持します。実返済は上流の接続・口座照合が復旧してから成行で行います。dryrunは新鮮な発注商品の気配がなければ返済済みにしません。

`Ctrl+C` または終了シグナルで新規を止め、未送信の新規判断を破棄し、今回の起動で所有する担当建玉を返済します。旧実建玉や手動建玉は対象外です。終了猶予は初期設定30秒。未返済・結果不明が残れば、異常終了として状態を残します。次の起動では旧未確定注文を照合してから、残った旧実建玉を手動管理へ移します。

場替わりで `session=null` が返っても正常な休場として待ちます。同一運転中の旧場に残った所有建玉・未確定注文を消して新場へ切り替えません。通信停止・市場停止・プロセス強制終了中の約定や場内返済は保証できません。トレーリングはアプリが計算するため、アプリや通信が停止している間は追尾できません。

送信結果不明の注文は再送しません。上流注文番号が分からないままの場合は、ログと実口座を照合して解消する必要があります。所有不明の注文や手動建玉を推測で自分の玉に取り込みません。

未確定注文がないときは、自分の建玉IDと実口座の残数も照合します。食い違いが出れば新規を止め、口座情報の非同期更新を待っても15秒間解消しなければ運転を停止します。別媒体からの手動返済を推測で吸収しません。

## 記録

注文・約定・判断根拠はSQLiteを正本とします。売買履歴の通常ファイル出力は、終了確定後の`log/{商品}/{セッション}.csv`（仮想は`_dryrun.csv`）と`log/sessionPL.csv`です。出力済みの履歴を利用者が削除した場合は再生成しません。

毎起動の旧状態はSQLiteへ監査保存し、約定履歴は追記で維持します。旧実建玉を手動管理へ外しても過去の新規約定を消しません。手動返済はアプリの返済として記録しないため、起動をまたいだ旧建玉の清算は口座記録と併せて確認します。

相対保存先は実行ファイルのある配布フォルダが基準です。既存の所有状態を持つ`data`・`log`を複製して同時運転しないでください。

| 保存先の例 | 内容 |
|---|---|
| `log/error.log` | 異常終了の日時・理由。設定読込エラーも記録 |
| `data/dryrun/topixmini/market.sqlite` | 原板、受信時刻、履歴世代、確定足準備情報、運転状態 |
| `data/dryrun/topixmini/TOPIXmini.sqlite` | 判断・送信待ち・上流注文番号・約定ID・所有玉・戦略状態 |
| `log/TOPIXmini/2026-10-28_Night_dryrun.csv` | 終了確定後の6列約定履歴 |
| `log/sessionPL.csv` | 商品・実仮想別の7列セッション集計 |
| `log/web/操作.jsonl` | 設定・モード変更の小さい操作記録 |
| `log/diagnostics/` | 明示操作で出力する対象場の分割診断ZIP |

実運転のSQLiteは`live`ディレクトリに分離します。終了CSVは同じ商品フォルダを使い、実売買のファイル名には`_dryrun`を付けません。SQLiteの実行IDと商品による分離は維持し、日経の例は`data/dryrun/nk225micro/NK225micro.sqlite`です。

終了CSVは立会終了後に未送信・未確定・未反映の処理が解消してから確定します。運転中の受信・判断は画面の「稼働」で確認し、詳しい保存記録が必要な場合はSQLiteから診断ZIPを書き出します。無約定を、受信停止や判断停止と区別できます。

既定30秒ごとの稼働JSONには、発注商品の新鮮な気配を使った `unrealized_yen` と担当別内訳を記録します。買い玉は買気配で売却、売り玉は売気配で買戻す費用前の評価です。気配が古ければ値を省略し、0円とは扱いません。TG04/PG04の `exit_diagnostics` は、実枚数と内部仮想候補を分け、R・追尾開始幅・追尾幅・出口水準・残玉予算を残します。候補の水準はラージ板による判断値で、発注商品の実約定価格や約定保証ではありません。

SQLiteの約定記録には日時・売買・枚数・価格・担当・理由・判断ID・上流注文ID・約定IDを記録します。新手法の担当は `core`/`addon`/`episode`、旧手法は `core`/`extra` です。費用前の実現損益、標準手数料、新規建玉ID、返済建玉内訳、照合根拠も保持します。費用後合計は実現損益から新規・返済の標準手数料を引きます。通常の終了CSVは手数料前の6列で、詳細は診断ZIPへ出力します。

raw板はSQLiteに全受信保存し、CSVへ板全量を複製しません。当場履歴は再取得した回も別入力として記録します。履歴取得や保存先変更でディスク使用量が増えるため、保管・バックアップは停止中に行ってください。実玉・未確定注文がある状態でDBを削除すると所有関係を失います。

全状態を毎回イベントへ複製せず、状態更新イベントは版・バイト数・指紋と約定追加件数を記録します。最新状態はsnapshot、原板はbooksへ保持します。閲覧用は[Viewer連携](Viewer連携.md)の約定・管理外移管だけを小容量出力します。旧モード別の詳細CSV・旧約定JSONL・`session_summary*.csv`と、`trace.jsonl`は、自動出力も起動時再生成も行いません。既存の旧ファイルは自動削除せず、旧DBの巨大な履歴も削除・縮小しません。

転送には `[startup] action="diagnostics"` と `diagnostic_session` だけで[診断ZIP](診断データの出力.md)を作れます。元DBは読取専用で、controllerへ接続しません。全約定を保持しつつ原板全量を除き、1ファイル8MiB以内に分割します。

## モジュールの分担

| 場所 | 役割 |
|---|---|
| `internal/strategy` | 入口・継続・出口・担当別配分。外部APIを呼ばない |
| `internal/e01` | 日中の基準判断と確定足特徴 |
| `internal/runner` | 履歴準備・時計・受信・判断と約定の接続 |
| `internal/execution` | 送信前保存、上限、担当別返済、部分約定、再送防止 |
| `internal/controller` | 生API・履歴・PUSH接続 |
| `internal/journal` | SQLite正本と終了CSV |
| `internal/diagnostics` | 既存SQLiteの読取専用診断・転送用ZIP |
| `internal/exitreport` | 異常終了の表示・ログ保存・Windows直接起動時の確認待ち |
| `internal/schedule` | 立会・米英の時間切替 |

戦略を差し替える際は `strategy.Portfolio` の `Observe`（判断）、`OnFill`（約定反映）、`OnOrderDone`（残数量の終了）、`Dump/Restore`（復元）を境界にします。発注受付時点で `OnFill` を呼ばないことが重要です。

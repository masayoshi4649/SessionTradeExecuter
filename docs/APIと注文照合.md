# APIと注文照合

接続先は `http://10.10.100.1:8080`。APIキーは controller が上流へ付与するため、このアプリにキーやAPIパスワードは設定しません。

| 用途 | メソッドとパス |
|---|---|
| 商品・限月・実銘柄ID | `GET /api/v1/sys/registrations/future` |
| 立会・注文・建玉・取得状態 | `GET /api/v1/orders/future?scope=all` |
| 銘柄属性 | `GET /api/v1/redirect/symbol/{銘柄ID}@2?addinfo=true` |
| 新規・返済 | `POST /api/v1/redirect/sendorder/future` |
| 未完了注文の取消 | `PUT /api/v1/redirect/cancelorder` |
| 旧版の所有条件予約の取消 | `POST /api/v1/orders/future/reservations/{予約ID}/cancel` |
| 生の注文明細 | `GET /api/v1/redirect/orders?product=3&details=true` |
| 生の建玉 | `GET /api/v1/redirect/positions?product=3&addinfo=true` |
| ラージ生板 | `GET /api/v1/history/{NK225またはTOPIX}/book` |
| 分足 | `GET /api/v1/history/{商品}/candles/{1minまたは5min}` |
| 受信 | `WS /api/v1/redirect/websocket` |

営業時間と送信市場は controller の `session`、実銘柄IDと限月は登録一覧を使います。円換算倍率・呼値はAPI未提供の規格として設定します。銘柄属性の `TradingUnit` は売買単位で、円換算倍率ではありません。

## 発注・返済

条件成立後、発注意図を SQLite に確定してから、生の先物APIへ一度だけ送信します。新規の条件予約はcontrollerへ作らず、トレーリングはアプリ側で計算します。旧台帳に残る所有条件予約がある場合だけ、起動時に上表の取消APIを使います。`Side` は買い `"2"`・売り `"1"`、`TradeType` は新規 `1`・返済 `2`。成行 `FrontOrderType=120`・FAK `TimeInForce=2` を使います。日経マイクロは非SORの日中23・夜間24を指定します。

FAKは一部だけ約定して残りが終了する場合があります。`OrderId` は受付番号であり、約定確認ではありません。`Details[].RecType=8` の約定明細と建玉ID・残数量を照合し、実際に約定した数量だけを反映します。終了状態 `State=5` でも、明細・数量の確認が終わるまで完了としません。約定ゼロの終了も別に通知します。

旧手法の担当は `core` と `extra`、TG04/PG04は `core`・`addon`・`episode` です。担当を全意図・建玉・約定へ記録し、返済対象は今回の起動で所有した同じ担当の建玉IDに限定します。新手法は返すIDと枚数を明示し、最古の利益玉1枚を対象から除外できます。指定外の玉・残数超過・他注文の予約重複は拒否します。片方向上限は今回の全担当を合算し、旧実建玉・他媒体・手動建玉を含めません。旧1枚と新上限10枚で口座全体11枚になっても、この上限には違反しません。

商品ごとのworkerは1商品だけを売買し、商品・実／仮想ごとに分離したSQLiteへ保存します。単一アプリから複数workerを運転できます。毎起動で新しい注文名前空間（Namespace）を作り、上流の注文ID・約定ID・建玉IDと結び付けます。表示用実行IDや戦略の判断IDだけでは所有を判定しません。別プロセスや前回の同日・同じ戦略番号の注文を今回の約定として取り込みません。旧履歴で別注文に使用済みの約定IDも再利用しません。

## 中断・再起動

タイムアウト、受付番号の欠落、送信前記録後の強制終了は「結果不明」です。自動再送しません。取消の受付も取消完了ではないため、約定・終了状態の照合を続けます。結果不明で上流注文番号もない場合は、自動照合で勝手に注文を同定せず停止します。

通常運転の停止・引け・静観開始で期限前に取り消すのは新規注文だけです。返済注文はその期限まで照合を待ちます。返済を送った直後、次の監視周期で自分から取り消す動作を防ぎます。

新しい起動では、旧所有注文の新規・返済とも終了を確認してから空の運転へ切り替えます。生注文は台帳の上流注文IDと商品・方向を照合して取消します。旧条件予約はcontroller世代・注文識別ID・商品が一致するものだけを取消し、別媒体の予約を列挙して一括取消することはありません。取消と競合した約定は旧履歴へ記録します。取消受付のみ・注文番号不明・期限内に終了照合できない場合は、新しい運転を開始しません。

SQLiteには送信前本文・担当・判断根拠・約定ID・所有建玉・戦略状態と約定反映位置を保存します。起動時は旧状態の監査保存と新状態への更新を1トランザクションで行い、確定済み全約定履歴を保ちます。旧実建玉は今回の所有集合から外して手動管理へ移し、自動返済しません。履歴の指標準備から過去注文・候補・残玉を復元せず、枚数や手法の変更後も新しい名前空間で始めます。CSV等の出力だけ失敗しても、確定済みSQLiteの約定は巻き戻しません。

SQLiteの約定記録は費用前の実現損益と標準手数料を別々に保持します。全新規・返済の標準手数料を引くと見積費用後合計になります。分割約定の費用は同注文の累積枚数から差額計上します。税金・J-NET等を含めた口座の実請求額ではありません。通常の[終了CSV](セッション損益.md)は粗損益だけを出し、手数料や建玉IDを含む詳細は明示操作の診断ZIPで確認します。旧詳細CSV・JSONLは自動出力しません。

返済建玉の内訳は口座残数の減少を照合して確定し、SQLiteの`Closed`へ保存します。上流明細が元建玉との対応を返さない場合の順序配賦は`ClosedBasis`へ記録し、診断ZIPの`返済内訳の根拠`にも明記します。残玉の予算は、他玉の返済注文が完了してから計算します。

## 入力と仮想価格

判断はTOPIX・日経225の**ラージ**を同時に観測します。発注商品がミニ・マイクロでも、判断入力をその薄い板へ切り替えません。一方、実約定は設定した発注商品の約定明細です。研究で用いたラージ気配による仮想価格と、ミニ・マイクロで実際に成立する価格は一致を保証しません。仮想実行の価格は runner が渡した観測価格で、注文APIを呼びません。

生板履歴は全文読取後に `X-History-Complete: true` を検証します。分足と生板、二市場の `sessionId`・`generation` が異なるものは混ぜません。controller再起動は同一セッションでも世代が変わります。履歴は現在セッションだけで、controllerが再起動すると以前のメモリー履歴は消失します。

WebSocketは上流断でも下流接続が残る仕様です。接続中だけで入力が新鮮と判断してはいけません。受信時刻、価格時刻、口座の取得時刻と stale を区別します。生JSONは未知フィールドを含めて保持します。なお上流の `BidPrice`・`AskPrice` は通常の英語慣用と逆の定義なので、買気配は `Buy1.Price`、売気配は `Sell1.Price` を基準にします。

仮想指定では通信クライアント自身も変更APIを遮断します。実運用への切替は設定と起動モードの確認が必要です。実注文はこの開発・試験では送信していません。

SQLiteの定期稼働記録には、今回の実保有と発注商品の気配による評価損益、TG04/PG04では候補と実保有を分けた出口水準を残します。最新状態・入力原文もSQLiteに保持し、`trace.jsonl`へは出力しません。既存traceは自動削除せず、起動時の再作成も行いません。`startup.action="diagnostics"` による[診断ZIP](診断データの出力.md)は、注文API・取消API・照会APIのいずれにも接続せず、既存DBだけを読み取ります。

# SQLite正本と終了CSV

`modernc.org/sqlite` を使い、CGOなしで動作する。`Open(DBパス, ログディレクトリ)` の呼出し形は互換用に維持するが、通常保存はSQLiteだけに行い、ログディレクトリへ旧派生ファイルを生成しない。既存E01の状態を同じパスへ移して自動変換する機能はない。

商品別の注文台帳と市場入力DBを分け、元のDB配置を維持する。同じDBの二重運転を防ぐプロセスロックは運転層が担当する。

## 保存範囲

| テーブル | 内容 |
| --- | --- |
| `snapshot` | 最後に確定した復元状態と改訂番号 |
| `trades` | 記録IDが一意な確定約定。担当・商品・判断根拠を含む |
| `sessions` | 約定がなくても記録する運転セッション |
| `report_sessions` | 商品・モード別の報告対象場、立会終了、出力済み印と反映した約定位置 |
| `books` | 受信原文、受信時刻、世代、商品、取込元、連番入力ID |
| `events` | 判断・照合・台帳変更・約定確定・入力保存の連番履歴 |

WAL、`synchronous=FULL`、接続1本を使用する。`Save(state, allTrades)` は状態、新たな約定、対応するイベントを同じトランザクションで確定する。既存約定の消失・内容変更・並べ替え・入力内ID重複は拒否する。同じ状態・全約定の再保存は約定や変更イベントを増やさない。

本体Storeと`PublishStoredViewer`・`FinalizeStoredReports`は同じDBを別接続で開く。各プールを1接続にしても、Storeのmutexだけでは別プールのwriterを排他できない。旧DEFERRED保存で約定・snapshotを読んだ後に別writerが確定すると、保存時の書込昇格が`SQLITE_BUSY_SNAPSHOT (517)`になる。writerが保持中なら`SQLITE_BUSY (5)`にもなる。これは[SQLite公式の分離動作](https://www.sqlite.org/isolation.html)に対応し、両Stored出力との人工試験で再現する。停止時のDB・スタックを取得したという意味ではない。

保存用の全接続を`openJournalSQLite`へ統一し、`BEGIN IMMEDIATE`で読取前に書込予約を確保する。ドライバ固定版`modernc.org/sqlite v1.36.3`の`Driver.Open`・`applyQueryParams`・`newTx`に従い、DSNの`_txlock=immediate`と複数の`_pragma`を使用する。物理接続が交換されても`busy_timeout=5000`・`synchronous=FULL`・`foreign_keys=ON`を再適用する。WALはDBに永続するため、`Open`で有効化と結果を確認する。`ReadOnly`指定の診断トランザクションはDEFERREDのままにする。

競合待ちはSQLiteの5秒までとし、保存本文・約定・注文をアプリ側で再実行しない。長い競合やI/O・制約エラーは元のエラーを返し、未確定トランザクションを巻き戻す。終了CSV・Viewer資料の保存失敗と正本約定の確定は従来どおり分離する。[待機設定の仕様](https://www.sqlite.org/pragma.html#pragma_busy_timeout)も参照。

2026年10月26日以降、通常の `台帳更新` イベントは、改訂番号・変更前後SHA256・状態のバイト数・新規約定数・参照先だけを記録する。全復元状態は最新の `snapshot` に保持し、チェックポイントごとに `events` へ重複複製しない。旧DBに既に存在する全量イベントは書き換えない。新方式は任意の過去チェックポイントの全状態を保存する方式ではない。

`ArchiveAndSave(state, allTrades, metadata)` は運転状態を明示的に切り替える場合だけ使う。切替直前の全snapshotを `起動時状態切替` イベントへ一回監査保存し、新snapshot・約定不変の検査と同一トランザクションで確定する。途中失敗では旧snapshotだけを維持し、切替イベントも確定しない。どの状態切替を許可するかは実行層が決定する。

`RecordBooks` はバッチ全体を1トランザクションで保存する。同じ原文でも別受信なら別入力IDを割り当てる。原文の空白も変更しない。途中で失敗したバッチのIDは呼出元へ返さない。入力保存イベントにはバッチの最初と最後の入力IDを記録し、原文そのものは `books` から参照する。

## 監査記録と旧自動出力の廃止

通常の`Open`・`Save`・`EnsureSession`・原板保存・イベント保存から、旧詳細CSV・約定JSONL・`session_summary*.csv`・`trace.jsonl`を生成しない。起動時再生成、既存ファイルへの追記、削除済みファイルの再作成も行わない。既存の旧ファイルは自動削除せず、内容を変更しない。

復元・監査に必要な約定、判断根拠、原文、状態は引き続きSQLiteに保存する。詳細CSV・JSONLが必要な場合は、`internal/diagnostics`の明示的な診断ZIP出力を使う。Webの小さい`操作.jsonl`は別層の操作記録として継続する。

`Trade.PnL`は費用前の実現額、`Fee`は片道の立会手数料を別に記録する。同じ注文が分割約定した場合、注文累計枚数に対する切捨て額の増分を各約定へ配賦し、注文合計の端数処理を一致させる。旧記録の欠落した費用は0のまま復元し、推定値で過去約定を書き換えない。

新規の`HoldID`と返済の`Closed`は建玉ID単位で追跡する。`ClosedBasis`は仮想指定順による配賦か、口座残数照合による配賦かを示す。複数の返済明細・複数玉の減少が一度に届いた場合、個々の明細と新規建玉IDの対応順を上流情報だけで証明できないため、指定順配賦の根拠を明示する。残玉を返済要求から除外することと、返済されたID集合・合計数量・全体損益の照合は別に行う。

`ProjectionError`型は旧呼出側との互換用に残す。通常の保存処理は派生ログを生成しないため、この型を新たに返さない。SQLite保存の失敗ではトランザクションを巻き戻し、Store自身に未確定の状態を保持しない。後述の終了CSV保存は別処理であり、その失敗を理由に確定済み約定を巻き戻さない。

この層は注文APIを呼ばない。「送信前の意図保存」「送信結果不明の照合待ち」「約定の所有関係と部分返済」「戦略への反映位置」は注文管理層が状態に含める。SQLiteへの保存と外部注文送信は単一トランザクションにはできないため、再起動を理由に不明注文を再送しない。

## 利用者向けの終了CSV

共通ログ保存先へ、次の2種類を出力する。旧詳細ログの保存先と混同しない。

- `{Product}/{Session}.csv`、仮想は`{Product}/{Session}_dryrun.csv`。`売買種別,price,qty,timestamp,損益,手法ID`の6列。
- `sessionPL.csv`。`利益,損失,収支,新規建合計qty,セッション,銘柄,モード`の7列。

`LongN/LongR`は買い玉の新規／売り返済、`ShortN/ShortR`は売り玉の新規／買い返済。新規損益は0。金額は費用前で、集計の収支は利益−損失。同じセッション・商品・モードを一意に更新し、`live/dryrun`を別行にする。約定IDの一意性は既存`trades`が担い、同場の再起動でも確定約定を重複加算しない。

`RegisterReportSession`で明示登録した場だけを対象にし、旧`sessions`から過去全場を自動移行しない。終了時計は呼出側の`Plan.End`。終了時刻だけでは出力せず、未送信の新規・返済待ち列、未確定注文、未反映約定がすべて解消してから出力する。保存snapshotの`runtime_state.Queue`も判定するため、途中停止中の未送信判断を終了済みと扱わない。OFFや手法時間枠の切替は立会終了ではない。管理外へ移した玉の手動返済や未確定の含みを生成しない。

時刻は`Trade.At`をRFC3339Nanoで保存する。手法IDは`Trade.MethodID`、当時の`Evidence`内の手法・プロフィール、最後に「不明」の順で扱い、終了時の現在設定で過去約定を書き換えない。

`report_sessions`の出力済み印で「初回出力待ち」と「利用者が出力を削除した状態」を区別する。2種類のCSVを書き出してから印を確定し、途中停止の再試行では同じキーを更新する。印確定後に削除されたファイル・集計行は補完しない。遅着約定の訂正は現存する対象出力だけに行う。Webの履歴APIは`sessionPL.csv`を都度読むため、DB正本に約定があっても削除した報告を復活させない。

報告出力の失敗は確定済み取引の巻戻し理由にしない。エラーを画面へ伝え、同じ報告を再試行しても二重行を増やさない。共有する集計CSVの読取・更新・置換は排他して、商品ごとの同時終了で他商品の行を失わないようにする。

## 確認

`go test ./internal/journal -count=1`

再保存とID重複、SQL挿入途中のロールバック、同値の別受信、バッチ失敗、同時受信、`Close`なしのプロセス終了後の復元を確認する。旧ログを生成・変更しないこと、正本と売買根拠の保持、運転切替の原子性も検査する。実注文APIは使用しない。

終了CSVは、正式終了時計、未送信・未照合・未反映の待機、四売買種別、当時の手法、費用分離、再起動、削除後の遅着、二ファイル間の保存失敗、同時商品・実仮想の分離、別プロセスの排他を人工試験で確認する。

SQLite競合は、旧DEFERRED順序の5/517再現、物理接続交換後の設定、IMMEDIATE開始時の待機と期限超過、読取専用tx、記号付きDBパス、本体保存と両Stored出力の同時反復を検査する。30所有玉・60約定について正本本文と順序、所有ID、円損益、費用、Viewer全片とCSV集計の重複・欠落がないことを照合する。
